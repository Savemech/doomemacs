#+TITLE: Experimental Windows installer

This fork maintains an experimental native Windows x86_64 installer. It is not an official Doom binary distribution. Framework code and modules are used without installer specific patches. Initial package synchronization requires internet access.

* Build

Requirements: Windows 10 version 1903 or newer, Windows PowerShell 5.1, Git, =just=, Windows =curl.exe= and =tar.exe=. Full 7-Zip is required for release archive verification. Allow at least 6 GB for downloads, one workspace and output, and more when retaining old workspaces or running WSL tests. Build tools, archives and executables are ignored by Git.

#+begin_src powershell
just                    # list commands; does not start a build
just init               # exact module gitlink, never latest
just bootstrap          # pinned portable NSIS, zstd, 7zr and actionlint
just doctor
just versions
just build-fast         # complete uncompressed development installer
just test               # focused checks + compiled NSIS lifecycle fixture
just test-runtime       # real native compilation, bundled Git and GUI client
#+end_src

Builds use =build/payloads.lock.json= and never select newer runtime versions implicitly. =build/release.json= contains the Windows revision; Doom's version comes from =.doom=. Emacs version labels, PE version fields and the font inventory are generated from these inputs. MinGit and its PortableGit support tools update together; GCC and libgccjit must match. A =build-info.json= in the bundle records the complete lock and source fingerprint.

By default workspaces live under =%LOCALAPPDATA%\doom-installer-build\repo-HASH\staging-HASH=. Set =$env:DOOM_BUILD_ROOT = 'W:\2WS\doom-emacs-build'= before invoking recipes to use another drive. Sources and payload pins select the workspace; a new input set gets a fresh directory, avoiding DLLs left by an older toolchain. Only Git-tracked framework/module sources and installer assets are copied; use =git add= for new files before staging. Ignored caches and personal configs are excluded.

=just fetch= downloads and verifies archives only. =just stage= assembles the payload. =just compile-fast= recompiles an existing workspace after editing installer scripts/UI; =just build-fast= also restages assets. Management scripts are embedded from source at compile time. Interrupted or contaminated workspaces are refused; =just restage= renames the owned directory to a sibling =.kept-...= directory, retaining all its files, then stages again. Unknown directories and installed runtime trees are never adopted automatically. There is no recursive cleanup recipe; retained builds require deliberate manual removal.

The PowerShell entry points remain available without =just=, for example =.\installer\build\build-installer.ps1 -SkipCompress=. =just= is a command index; the same scripts drive CI.

* Maintenance every few months

Commit current work first. Upstream fetch/merge, dependency discovery, pin changes and building are separate operations:

#+begin_src powershell
just upstream-fetch
just upstream-merge origin/master
just pin-modules
just updates                      # discover; no pin changes
just update emacs                 # latest stable GNU UCRT64 archive
just update git                   # MinGit + matching PortableGit
just update toolchain             # coherent MSYS2 runtime dependency closure
just update ripgrep
just update fd
just update fonts
# Or: just update all
# An explicit release is also accepted, e.g. just update emacs 31.1
git diff
just bump-release                 # once per new Windows release
just doctor
just build-fast
just test
just test-runtime
just test-wsl Ubuntu-20.04         # optional; explicitly choose your distro
# Review and commit sources, pins and Windows revision, then:
just release                      # checks, compressed build, runtime checks, 7z verification
just artifacts                    # paths + SHA256; does not publish
#+end_src

=upstream-merge= defaults to =origin/master=; this fork uses =origin= for upstream and =fork= for its GitHub remote. Supply another ref if your remotes differ. It requires a clean branch and creates a backup branch before merging. Merge conflicts are left for manual resolution; it never resets or cleans your working tree. =pin-modules= aligns the lock with the committed gitlink after the merge; =init= checks out that gitlink without forcing local module changes away.

=updates= reads release metadata and, for MSYS2, retains a downloaded repository snapshot. =update= prepares candidate pins, downloads changed archives and verifies their SHA256 before replacing the lock atomically; a failure keeps the previous lock. The previous JSON is also retained in the ignored cache. Updates are not installed into your running Emacs. Review the diff, run tests and commit the lock to Git. Downgrading dependency pins means restoring a reviewed lock from Git and building again; this does not implement rollback of an installed application or its package data.

The MSYS2 updater resolves GCC/libgccjit, binutils, CRT, pthreads and their runtime dependencies from one repository snapshot, including current/legacy CRT package names. It supports unversioned and exact-version dependencies; unsupported constraints or unresolved dependencies stop the update for review. It is deliberately not a general pacman replacement. Later MSYS2 archives may disappear from mirrors: preserve verified archives when reproducibility across long periods matters. Build tool updates are separately reviewed edits to =buildTools= in the lock; =bootstrap= never follows latest.

=test-runtime= compiles and executes a small native Lisp function with the bundled Emacs/toolchain, checks Git's shell utilities with host Git removed from PATH, and opens an isolated GUI client session. Tests use temporary homes. =test-wsl= additionally retains an isolated runtime copy and uses temporary Linux homes; it does not install shell integration into your real WSL profile. A release requires a clean committed checkout and full 7-Zip; no recipe installs into your personal Emacs, publishes a GitHub release, or merges upstream automatically.

* Package compilation and reinstall speed

See [[file:default-runtime.org][the default runtime dependency audit]] for feature coverage, optional dependencies and =just test-defaults=. The runtime includes native zstd/XZ/7za, gzip/bzip2, Bash, patch, a pager, SSH helpers, ShellCheck and Pandoc. They take precedence over host package-manager shims and the Windows WSL bash launcher. Both the editor and clients receive UTF-8 application manifests so processes can run from Unicode working directories. The fresh-machine CI job stages and tests these operations without using host Git/Unix tools.

Setup always performs the required package sync. Native ahead-of-time compilation
is optional and unchecked by default; Emacs can optimize loaded Lisp in the
background. Select the native pre-compilation component, or pass =-AOT= to the
PowerShell engine, to wait for this optimization during setup. =-NoAOT= remains
accepted and takes precedence. =-RebuildPackages= explicitly rebuilds all packages.

After a successful sync, the manifest records the Emacs version, native ABI,
system configuration, executable hash, bundled compiler/runtime archive hashes
and installation location. Compatible reinstalls use incremental sync. A change
to this signature, a failed/interrupted previous sync, or an existing package tree
without a confirmed signature requests =--rebuild=. A legacy installation may
therefore need one rebuild before subsequent reinstalls become incremental.
Existing native caches are retained; Emacs separates native code by version/ABI.
Config and Doom changes still go through Doom's normal package dependency checks.
Setup does not request an upgrade of all packages with =-u=.

Both compiler output streams are drained concurrently and streamed as plain text
to NSIS, removing ANSI colors and cursor movement. A failed sync invalidates the
success record before any build starts, so old packages cannot mask a failure.

This reduces compilation work; setup still extracts the full payload in place.
Version directories, transactional switching, editor session handoff and
rollback are not implemented. It does not terminate Emacs or WSL to obtain a
quick restart, and no instant reinstall timing is claimed.

* Installation and removal

The default root is =%LOCALAPPDATA%\Programs\DoomEmacs=. The installer bundles GNU
Emacs, MinGit, ripgrep, fd and an MSYS2 UCRT64 native compilation toolchain. Only
the root's =bin= directory is added to the user's PATH. Launchers set their
environment per process; they do not change a persistent HOME variable.

MinGit is supplemented with =which.exe= and =cygpath.exe= from the matching
PortableGit release. Magit uses both to discover the native Git executable and
translate its MSYS PATH. The archive is hash-pinned and extracted with 7-Zip;
its self-extracting executable is never run. Runtime tests remove host Git tools
from PATH so a full Git installation cannot hide missing bundled utilities.

The optional, initially selected font component includes four MesloLGM Nerd Font
styles and Symbols Nerd Font Mono from Nerd Fonts v3.5.1, with upstream license
notices. Only these files are extracted from the pinned release archives.
=nerd-icons= uses Symbols Nerd Font Mono independently of the editor's text font.
New configurations select Meslo at 12 points; existing configurations and themes
are kept. Font size/theme remain user preferences, not upgrade migrations.

Font files stay under =INSTALL_ROOT/fonts= in versioned folders. Missing families
are registered for the current Windows user at
=HKCU\Software\Microsoft\Windows NT\CurrentVersion\Fonts= and loaded for the
current session. Existing families are not replaced or adopted. =font-state.json=
records our exact registry values, paths and hashes before registration.
Uninstall removes only still-matching owned values, keeping unrelated/replaced
values and existing fonts. Changed owned font files block reinstall before
extraction, and block removal for review. Clearing the font component or passing
=-NoFonts= to the engine preserves existing registrations. Applications already
running may need to restart to refresh their font cache.

The default user configuration is =%USERPROFILE%\.config\doom=. Existing files
are kept. Windows show the full configuration paths, identify a missing folder,
and separately display an existing =%USERPROFILE%\.doom.d=. They explicitly state
that configuration stays in place and no backup or automatic migration is made.
Application, cache, PATH and configuration locations are shown in individual
read-only text fields: select a field and use Ctrl+A / Ctrl+C to copy its path.

Opening setup again offers reinstall/repair or removal of the bundled tools.
Removal is also registered in Windows Settings. The ownership manifest records
which paths and PATH entries were created by setup. Default removal keeps user
configuration and separately installed tools.

#+begin_src powershell
# Unattended install, without shortcuts:
.\DoomEmacs-VERSION-x86_64-setup.exe /S /NoShortcuts
# Unattended removal, keeping configuration:
.\DoomEmacs-VERSION-x86_64-setup.exe /S /Uninstall
# Inspect recovery of an incomplete bundle:
.\installer\repair-doom.ps1 -InstallRoot 'C:\path\to\DoomEmacs' -WhatIf
#+end_src

The recovery helper handles early prototype bundles without an ownership
manifest. It adopts only recognized payload paths; unrelated root content and
the root itself are preserved. It does not download packages.

.\installer\test\env-path-selftest.ps1
.\installer\test\install-guard-selftest.ps1
.\installer\test\uninstall-plan-selftest.ps1
.\installer\test\diff-selftest.ps1
.\installer\test\snapshot.ps1 -SelfTest
.\installer\test\installer-selftest.ps1 -MakeNsis 'C:\path\to\makensis.exe'
.\installer\test\wsl-bridge-selftest.ps1
.\installer\test\wsl-selection-selftest.ps1
.\installer\test\package-sync-selftest.ps1
.\installer\test\font-integration-selftest.ps1
# Real bundled shell / Magit dependency checks:
.\installer\test\git-tools-selftest.ps1 -InstallRoot 'C:\staging'
.\installer\test\git-tools-selftest.ps1 -InstallRoot 'C:\installed' -CheckMagit
# Optional real WSL/Windows runtime checks, using temporary Linux homes:
.\installer\test\wsl-bridge-selftest.ps1 -Distribution Ubuntu
.\installer\test\windows-client-selftest.ps1 -EmacsRoot 'C:\staging\emacs' -Distribution Ubuntu
.\installer\test\wsl-cli-selftest.ps1 -Distribution Ubuntu -InstallRoot 'C:\staging'
#+end_src

The lifecycle test compiles the actual NSIS source against a tiny fixture payload
and exercises install, reinstall, legacy recovery, failed sync and removal. It
uses a temporary profile and uninstall registry key. Its temporary user PATH
entry is removed in =finally=. The CLI is a stub: this proves packaging and
lifecycle behavior, not real package downloads or editor startup.

=just test= also validates GitHub Actions YAML with pinned =actionlint=. The fork does not depend on the broken =doomemacs/ci@legacy= commit-lint workflow. The inherited scheduled issue triage is restricted to the upstream repository, so it does not close or lock threads in this fork.

The snapshot/diff tools support before/after footprint inspection. A full clean
Windows Sandbox installation, editor launch and removal cycle remains required
before recommending a release. Local host smoke tests do not establish that a
clean machine has no missing dependencies.

* Optional WSL bridge

Select =Enable Windows Doom commands in WSL= during setup and choose an installed
user distribution. The distribution is identified by its registration id, not
only its name. Docker Desktop's internal distributions are excluded. WSL and
Windows executable interoperability must already work. Windows 10 1903+ is
required. Automatic shell integration supports Bash, Zsh and POSIX login shells.

The selected Linux user receives commands in
=~/.local/share/doom-windows/INSTALL_ID/bin=. Marked blocks in =.profile= and
=.bashrc= (and an existing/default Zsh =.zshrc=) add this directory to PATH.
These commands take precedence in that shell. Reopen the shell after setup.
The user's existing EDITOR and Linux Emacs installation are preserved.

#+begin_src sh
doom sync              # Windows Doom, packages and config
doom doctor            # Windows installation diagnostics
doom help
doom-wsl ./src/main.rs  # open the WSL file in the Windows GUI server
doom-wsl --new-frame ./src/main.rs
EDITOR='doom-wsl --wait' git commit
#+end_src

Every =doom= argument is forwarded unchanged to the selected Windows installation
through its bundled shell and Emacs. Its working directory is the Windows
installation root, not the Linux shell's current directory. The =doom-wsl=
command resolves Linux filenames (including relative names) to Windows paths
using =realpath= and =wslpath=. Arguments use base64/NUL framing instead of being
interpolated into shell or Lisp code. Linux projects remain on the WSL disk;
editing them still requires that disk to be accessible. Windows tools are used
for tooling; this feature does not configure Linux LSP/build tools through TRAMP.

The GUI launcher starts a Windows-local, authenticated server when integration
is enabled. =doom-wsl= connects to it, or starts the Windows GUI when needed.
Restart any old editor instance once after enabling integration. Server state
lives in =bridge-state/server= inside the Windows installation; no listener is
opened on WSL/network interfaces. The client executable's application manifest
opts into UTF-8 so Unicode paths do not pass through the system ANSI code page.
File contents retain their normal buffer encoding.

Native Windows Emacs cannot combine GUI and text frames in one session.
=doom-wsl --tty= therefore returns an explanation rather than starting an
unrelated Linux editor. =--wait= uses the normal Emacs server completion workflow
(=C-x #=) for programs such as Git.

Setup can also be driven with =/WslDistro=Ubuntu=, or by passing
=-WslDistro Ubuntu= to the PowerShell engine. Rerunning setup can add another
distribution; existing integrations are kept. Every interactive installation
shows the WSL page, including reinstalls and when the previous distribution is
missing. An available previous registration is suggested by its id, even after
renaming. A missing registration is reported without selecting a replacement
by name or removing its saved history. Clearing the checkbox preserves existing
connections. The installer does not install, upgrade or unregister distributions.

WSL integration records are mirrored under the installation's HKCU uninstall key
as =WslIntegrations= (JSON), =LastWslDistributionId= and =LastWslDistribution=.
The JSON files remain the ownership/recovery metadata; the registry supports
future setup selection. Older installations without these registry values are
recognized from their existing files. The ownership metadata is stored
in =wsl-bridge.json= and the installation manifest before Linux hooks are changed.
Removal targets the recorded Linux user, checks script hashes and deletes only
the exact managed PATH blocks. Edited scripts/blocks are preserved with an error.
If the distribution or its disk is inaccessible, Windows removal stops before
deleting the scripts and manifest, so cleanup can be retried. An unregistered
distribution may still have detached backing data; a replacement with the same
name is not touched. Missing registrations currently skip cleanup; this is not
proof that all files from the previous integration were removed.

Deleting the Windows folder directly bypasses this cleanup and leaves PATH and
WSL hooks. Use the installer's maintenance option or Windows Settings instead.
The review page lists these changes and the applicable no-warranty notice.

* Limitations and review questions

- The shipped Doom tree is a snapshot without Git metadata. Updating the
  framework requires another bundle; =doom upgrade= cannot update the core.
- =-DoomDir= on the engine is not propagated to the CMD launchers. Use the default
  configuration location until custom paths are implemented consistently.
- ARM64 and machine-wide installation are outside this proposal.
- GUI launch through a CMD file may briefly display a console window.
- Pinned SHA256 hashes detect changes to downloaded artifacts, but do not
  authenticate their publisher. GPG signature verification is not implemented;
  first pinning without a publisher digest uses trust-on-first-use.
- Redistribution review is still needed for every bundled component, including
  applicable license files, source availability and corresponding source offers.
- Release ownership, signing, hosting and acceptance of this packaging approach
  require maintainer agreement. No automated binary release is proposed here.

The installer and supporting changes include AI-assisted work. The proposed PR
must disclose this and comply with the upstream contribution policy.
